这个方案的**潜在创新集中在协作算法**：把多 Agent 的不同判断，转化为具体、可验证的程序前提，再通过有判别作用的查询更新分析。

**最需要收紧的，是“分歧诊断员”和“查询设计员属于全新角色”的说法。**

**对于语义分歧诊断 Agent，已有研究已经覆盖了哪些部分？**

- **发现分析中的问题**：MAVUL 的安全架构师检查分析并推动修正。\([arxiv\.org](https://arxiv.org/html/2510.00317v1?utm_source=chatgpt.com)\)

- **检查漏洞假设是否成立**：VulAgent 的 AssumptionPruner 检查假设状态；其提示还要求判断，某个假设失效是否会使触发路径失败。也就是说，“识别影响判断的前提”已经有直接相关机制。\([aclanthology\.org](https://aclanthology.org/2026.findings-acl.928.pdf?utm_source=chatgpt.com)\)

- **比较多个候选的假设和行为差异**：SHELDON 的 ComparativeAnalysis 已明确承担这一任务。它是流程阶段，不一定叫“分歧诊断 Agent”，但功能需要纳入比较。\([arxiv\.org](https://arxiv.org/html/2610.18025v1?utm_source=chatgpt.com)\)

因此，你可以重点争取的进一步能力是：

> **把多个漏洞解释对齐到同一危险操作、对象、变量状态和调用路径，识别真正的前提差异，并输出可以交给程序分析后端检查的争议命题。**
> 
> 

例如，双方都说“长度已检查”，但一个讨论检查时的 `n₀`，另一个讨论调用后的 `n₁`。你的 Agent 需要定位这个程序状态差异，而不只是总结双方意见。

- DREA 已根据漏洞假设规划仓库探索。

- 序贯模型诊断已系统研究区分解释、优化查询数量与查询成本。\([ojs\.aaai\.org](https://ojs.aaai.org/index.php/AAAI/article/download/30609/32771?utm_source=chatgpt.com)\)

**独立事实调查和符号执行角色，也应采用类似定位。**

“独立事实调查员”可以增加信息隔离：调查员只看到问题、程序范围和证据要求，暂时不知道哪个答案有利于报漏洞。但这只能作为一个**待验证的协议设计**，需要证明它确实减少确认偏差；不能仅凭独立上下文就称首次提出。

**1．Joern：从“提供代码骨架”升级为“围绕争议提取证据”。**

Joern 的 CPG 及查询语言适合结构化定位程序元素；其数据流查询可以返回来源及数据流路径，跨过程分析则依赖调用解析和函数语义等机制。\(Joern Documentation\)

你原先的“查询代码骨架”可以保留为第一阶段，但建议把骨架定义得更明确：

> **围绕待审危险操作，提取代码结构、候选依赖、相关检查及尚未解析的关系。**
> 
> 

例如，针对一次 `memcpy`，生成：

```Plain Text
目标操作：copy_items 中的 memcpy
目标参数：out->data
复制长度：n * sizeof(Item)

相关检查：
  n <= out->capacity

待追踪关系：
  out->data 的分配来源
  out->capacity 的赋值来源
  初始化函数到当前调用点的参数映射
  检查与使用之间的相关修改

尚未解决：
  是否存在其他初始化路径
  部分调用目标是否能够解析
```

这份骨架有三个直接用途。

尤其要注意：**代码骨架是导航和分析输入，不能直接作为完整程序语义。** 符号执行 Agent 应根据骨架返回真实源码及必要依赖，不能把删减后的摘要直接当成原程序运行。

Joern 对未解析调用也有明确的处理边界，例如可能关联到外部方法节点，缺少可靠的被调函数信息。因此，你的查询结果应保留“未解析依赖”，而不是让模型自行补成确定事实。\(How Interprocedural Data\-flow Works in Joern\)

**2．GraphRAG：建议重点存储“调查经验”，并保留结论的来源和适用范围。**

严格来说，GraphRAG 是图结构支持的检索增强方法，底层存储还需要独立设计。其局部检索可以结合图中的实体、关系及原始文本片段，为模型组织上下文。\(GraphRAG\)

在你的方案中，最值得保存的历史信息是：

> **遇到什么争议，执行了什么查询，获得了什么证据，这些证据在哪些条件下改变了判断。**
> 
> 

建议分成三类记忆：

例如，一条历史经验可以是：

```Plain Text
争议模式：容量单位与复制单位可能不一致

推荐调查：
  追踪目标对象的分配表达式
  追踪容量字段的赋值与参数映射
  检查相关路径上的字段修改

适用条件：
  能定位目标对象及其初始化关系

常见失败：
  多个初始化路径未区分
  分配函数为外部实现
  查询遗漏了相关写入

后续动作：
  按调用上下文拆分查询
  必要时构造符号执行任务
```

这样的记录能够帮助规划“怎样查”。历史案例中的“某字段表示字节容量”，仍需在当前程序中重新核实。

**3．两类图建议分别维护，通过源码锚点关联。**

可以采用以下结构：

**5．沿用容量例子，可以看到四部分怎样协作。**

待审逻辑为：

```C
if (n > out->capacity)
    return;

size_t bytes = n * sizeof(Item);
memcpy(out->data, src, bytes);
```

一次完整流程可以是：

1. **Joern 提取初始骨架**：定位复制操作、长度表达式、容量检查，以及需要追踪的字段。

2. **两个分析员独立判断**：风险分析员怀疑单位不一致；防护分析员提出“容量可能按元素分配”的条件性解释。

3. **分歧诊断员定位前提**：当前判断依赖实际分配大小与 `capacity` 的关系。

4. **GraphRAG 检索经验**：返回“先查分配和字段赋值，再检查路径及修改”的调查模板。

5. **查询设计员生成当前任务**：指定当前对象、调用范围和结果分支，要求追踪分配来源。

6. **事实调查员执行 Joern 查询**：返回相关源码和参数映射；若仅覆盖一条初始化路径，明确记录这一范围。

7. **必要时调用符号执行 Agent**：使用真实初始化逻辑，检查检查条件能否通过且复制长度超过分配容量。

8. **更新审计图**：保存证据，撤回失去依据的防护推断，保留尚未确认的条件。

未来遇到相似问题，系统可以复用第 4 步的**调查策略**；当前对象的分配关系仍要重新查询。

Joern 的 CPG 及查询语言适合结构化定位程序元素；其数据流查询可以返回来源及数据流路径，跨过程分析则依赖调用解析和函数语义等机制。\(Joern Documentation\)

你原先的“查询代码骨架”可以保留为第一阶段，但建议把骨架定义得更明确：

> **围绕待审危险操作，提取代码结构、候选依赖、相关检查及尚未解析的关系。**
> 
> 

例如，针对一次 `memcpy`，生成：

```Plain Text
目标操作：copy_items 中的 memcpy
目标参数：out->data
复制长度：n * sizeof(Item)

相关检查：
  n <= out->capacity

待追踪关系：
  out->data 的分配来源
  out->capacity 的赋值来源
  初始化函数到当前调用点的参数映射
  检查与使用之间的相关修改

尚未解决：
  是否存在其他初始化路径
  部分调用目标是否能够解析
```

这份骨架有三个直接用途。

尤其要注意：**代码骨架是导航和分析输入，不能直接作为完整程序语义。** 符号执行 Agent 应根据骨架返回真实源码及必要依赖，不能把删减后的摘要直接当成原程序运行。

Joern 对未解析调用也有明确的处理边界，例如可能关联到外部方法节点，缺少可靠的被调函数信息。因此，你的查询结果应保留“未解析依赖”，而不是让模型自行补成确定事实。\(How Interprocedural Data\-flow Works in Joern\)

**2．GraphRAG：建议重点存储“调查经验”，并保留结论的来源和适用范围。**

严格来说，GraphRAG 是图结构支持的检索增强方法，底层存储还需要独立设计。其局部检索可以结合图中的实体、关系及原始文本片段，为模型组织上下文。\(GraphRAG\)

在你的方案中，最值得保存的历史信息是：

> **遇到什么争议，执行了什么查询，获得了什么证据，这些证据在哪些条件下改变了判断。**
> 
> 

建议分成三类记忆：

例如，一条历史经验可以是：

```Plain Text
争议模式：容量单位与复制单位可能不一致

推荐调查：
  追踪目标对象的分配表达式
  追踪容量字段的赋值与参数映射
  检查相关路径上的字段修改

适用条件：
  能定位目标对象及其初始化关系

常见失败：
  多个初始化路径未区分
  分配函数为外部实现
  查询遗漏了相关写入

后续动作：
  按调用上下文拆分查询
  必要时构造符号执行任务
```

这样的记录能够帮助规划“怎样查”。历史案例中的“某字段表示字节容量”，仍需在当前程序中重新核实。

**3．两类图建议分别维护，通过源码锚点关联。**

可以采用以下结构：

审计记忆图可包含这些关系：

```Plain Text
风险主张 ──依赖于──> 程序前提
防护主张 ──依赖于──> 程序前提
争议 ──涉及──> 程序前提
查询 ──检查──> 程序前提
证据 ──支持/否定──> 程序主张
经验模板 ──适用于──> 争议模式
审计记录 ──锚定到──> 当前程序位置
```

每条证据还应保存：

- 源码版本、文件、函数和位置；

- 查询及工具配置；

- 调用上下文和分析范围；

- 是否依赖函数摘要、stub 或其他假设；

- 当前状态：候选、已支持、已否定、无法判定。

**模型生成的推断应保存在审计图中，并明确标为推断。** 不应把它直接写回 CPG，伪装成静态分析已经确认的关系。

跨次构图时，也不宜只依赖临时节点编号；应结合源码快照、相对路径、函数签名和代码片段哈希来核对锚点。

**4．接入六个 Agent 后，数据流可以这样安排。**

职责最集中的交接点是：

> **分歧诊断员产生结构化争议 → GraphRAG 检索候选调查策略 → 查询设计员结合当前 CPG 选择查询 → Joern 或符号执行后端执行 → 结果进入证据账本并更新分析。**
> 
> 

这里 GraphRAG 提供的是候选经验；查询是否适用、结果是否足够支持判断，仍由当前程序证据决定。

**5．沿用容量例子，可以看到四部分怎样协作。**

待审逻辑为：

```C
if (n > out->capacity)
    return;

size_t bytes = n * sizeof(Item);
memcpy(out->data, src, bytes);
```

一次完整流程可以是：

1. **Joern 提取初始骨架**：定位复制操作、长度表达式、容量检查，以及需要追踪的字段。

2. **两个分析员独立判断**：风险分析员怀疑单位不一致；防护分析员提出“容量可能按元素分配”的条件性解释。

3. **分歧诊断员定位前提**：当前判断依赖实际分配大小与 `capacity` 的关系。

4. **GraphRAG 检索经验**：返回“先查分配和字段赋值，再检查路径及修改”的调查模板。

5. **查询设计员生成当前任务**：指定当前对象、调用范围和结果分支，要求追踪分配来源。

6. **事实调查员执行 Joern 查询**：返回相关源码和参数映射；若仅覆盖一条初始化路径，明确记录这一范围。

7. **必要时调用符号执行 Agent**：使用真实初始化逻辑，检查检查条件能否通过且复制长度超过分配容量。

8. **更新审计图**：保存证据，撤回失去依据的防护推断，保留尚未确认的条件。

未来遇到相似问题，系统可以复用第 4 步的**调查策略**；当前对象的分配关系仍要重新查询。

**6．PrimeVul 实验中，历史信息需要有明确的写入边界。**

建议第一版采用：

- **长期经验库**：只由训练集和允许的外部资料构建，测试前冻结。

- **当前审计图**：每个测试样本独立更新，结束后保存为实验轨迹。

- **测试期间**：不把先前测试样本的判断自动加入长期库。

- **漏洞版与修复版**：分别分析，禁止共享另一版本的结论、补丁说明或配对答案。

- **程序缓存**：按源码版本、上下文、工具配置和依赖条件核对，不能只按函数名复用。

如果以后研究持续学习，可以单独设计按时间顺序更新的实验协议。第一版先使用冻结记忆，更容易解释方法收益。

**7．论文中应怎样定位这两部分？**

Joern、GraphRAG 的集成本身适合作为系统实现基础。已有 LLMxCPG 使用程序图组织漏洞上下文，CLEAR 使用知识图辅助推理，因此“加入图分析和图检索”难以单独承担主要创新。\(www\.usenix\.org\)

你可以争取证明的进一步机制是：

> **以程序语义分歧为检索入口，从历史调查经验中提出候选查询，再利用当前程序结构、验证能力与成本选择调查动作。**
> 
> 

这仍需实验支持。建议至少比较：

除检测指标外，应观察：重复查询比例、有效证据获取成本、历史经验误用率和判断修正率，并分别报告索引构建成本与在线成本。

**实施顺序建议是：先保留 Joern，跑通分歧诊断和查询协议；再加入小规模、带来源的历史经验库；最后验证 GraphRAG 的关系检索是否值得。** 如果普通结构化记录或向量检索已能满足需求，可以保持轻量实现，把科研投入集中在关键前提定位与查询决策算法上。

**3．最值得主张的三个候选创新**

**① 竞争解释之间的程序前提分歧诊断**

目前的“分歧诊断员”应当完成一个明确任务：

输入两组分析，输出：

```Plain Text
共同讨论的操作、对象和入口
双方共同接受的事实
双方结论分别依赖的前提
真正不相容的前提
尚缺证据、但并不相互矛盾的前提
影响最终结论的待调查前提
```

例如：

```Plain Text
风险解释：
复制数量会增加，而目标分配没有相应增加。

保护解释：
调用者已经为额外数据预留容量。

决定性前提：
实际分配大小是否包含额外数据。
```

这里需要实现**对象、变量版本、路径和调用上下文的对齐**。两个分析员分别讨论不同对象或不同路径时，不能误判为冲突。

相对于已有前提验证，你新增的任务是：

> **从多个分析之间的差异，反向定位需要验证的前提。**
> 
> 

不要把“提取前提”本身写成首创，也不必宣称能得到全局最小分歧集合。

**② 面向竞争解释的区分性查询选择——最重要的贡献**

查询设计员不能只输出“查看调用者”。它必须提前给出：

```Plain Text
查询对象：目标缓冲区的分配表达式

结果 A：分配包含额外数据
更新：排除“未预留额外容量”这一风险解释

结果 B：分配仅覆盖原始数据
更新：排除“调用者已预留容量”这一保护解释

结果 C：存在未解析的分配路径
更新：保留未决状态，进一步限定调用上下文
```

随后，系统在多个查询之间选择：

- 哪个查询能够区分当前的重要解释？

- 是否会影响最终判断？

- 哪个更便宜、更可能得到确定结果？

- 是否已有证据，或存在等价查询？

**创新点在于把“下一步查什么”作为可以优化、可以单独评价的决策任务。**

但也要承认：信息增益、主动查询和成本敏感决策已有研究基础。你的贡献应是它们在**程序语义前提、分析工具和多 Agent 协作**上的具体算法实现。

**③ 查询结果约束的分析更新协议**

工具返回事实后，不能简单让所有 Agent“重新考虑一下”。

应建立明确的依赖关系：

```Plain Text
源码证据
    → 支持或否定某项前提
    → 更新依赖该前提的解释
    → 更新对应候选漏洞
```

例如，证明“调用者预留了额外容量”，只能排除当前的容量不足解释，不能顺带宣布整个函数安全。

这个协议至少需要处理：

- 哪些主张必须撤回，哪些仍然有效；

- 新证据是否适用于同一个对象和调用路径；

- 工具结果不确定时，哪些结论继续保持未决；

- 是否出现重复调查或与既有事实冲突的更新。

**证据引用和三态判断本身都不足以成为强创新；更值得研究的是证据如何沿依赖关系约束协作过程。**

**6．怎样证明优势来自协作算法？**

- Token、工具调用次数、时间；

```Plain Text
危险操作：copy_items 中的 memcpy
```

实现分四步：

第一版只追求**局部、可检查的关键前提集合**。若使用最小冲突技术，只对已形式化的部分讨论其性质，不宣称找到了全局最小语义分歧。

## **6．核心算法之二：生成具有预先声明结果含义的查询。**

建议设计统一的查询中间表示：

```Plain Text
QuerySpec
```

## **7．符号执行 Agent：围绕未决前提做验证。**

建议将符号执行接入查询调度，而不是对每个样本固定运行。

适合调用的情况包括：

- 静态调查已确定对象和容量关系，但路径可行性仍不清楚；

- 多个条件跨函数组合，局部范围分析无法判断；

- 防护是否足够，取决于输入、分支和算术关系的联合约束；

- 需要验证一个静态候选是否存在模型内见证。

第一版可选 KLEE 作为后端，并固定编译器、引擎和求解器版本。KLEE 使用 LLVM bitcode，并提供符号输入、路径探索和错误输出；外部调用策略也可能具体化符号参数，因此环境设置必须纳入记录。\(KLEE\)

该 Agent 的执行步骤为：

1. **检查验证资格**：能否恢复相关源码、类型与依赖？

2. **定义目标命题**：明确检查的是哪次访问、哪个对象及哪种违例。

3. **选择入口**：优先使用能保持对象初始化关系的真实调用链。

4. **构建 harness**：加入符号输入和有来源的环境约束。

5. **审查环境**：检查 stub、输入假设和源码映射，禁止为得出目标结论而修改检查逻辑。

6. **调用引擎**：在明确边界内搜索。

7. **解释结果**：返回证据状态及适用范围。

建议采用以下返回状态：

每次返回都附带：

```Plain Text
源码版本与映射
入口和目标操作
输入域与对象分配关系
替代函数及其契约
探索边界、终止原因
见证路径或分析日志
尚未验证的环境假设
```

**找到模型内反例、证明真实调用可达、在原项目重放成功，是不同证据层次。** 可将具体重放作为额外的混合验证实验，但不能将其收益计入“仅源码分析”的结果。

同时设置两个主要配置：

- **基础配置**：源码、程序图和 SMT 查询。

- **符号增强配置**：基础配置加按需符号执行。

这样可以检验协作算法自身的贡献，以及符号执行的额外收益。SAILOR 已包含环境生成和反馈修正，因此本研究应重点比较**验证任务如何从争议中产生、如何调度以及如何用于更新判断**。\([arxiv\.org](https://arxiv.org/abs/2604.06506?utm_source=chatgpt.com)\)

**一、释放后使用：请求释放了对象，审计视图却还在引用**

这个案例包含一种常见的生命周期约定：

- `Request` 初始持有对象的一个引用。

- `View` 可以借用对象，也可以增加引用计数、持有自己的引用。

- 请求校验失败时，释放请求持有的引用。

- 错误审计随后读取 `View`。

问题取决于：**审计视图是否拥有足以覆盖审计阶段的独立引用？**

**1．待检测代码**

```C
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>

typedef struct {
    unsigned refs;
    size_t len;
} Blob;

typedef struct {
    Blob *payload;
} Request;

typedef struct {
    Blob *blob;
    bool owned;
} View;

static Blob *blob_new(size_t len) {
    Blob *b = malloc(sizeof(*b));
    if (b) {
        b->refs = 1;
        b->len = len;
    }
    return b;
}

static void blob_get(Blob *b) {
    ++b->refs;
}

static void blob_put(Blob *b) {
    if (--b->refs == 0)
        free(b);
}

static View open_view(Request *r, bool retain) {
    View v = { r->payload, retain };

    if (retain)
        blob_get(v.blob);

    return v;
}

static bool validate_request(Request *r, bool reject) {
    if (!reject)
        return true;

    blob_put(r->payload);
    r->payload = NULL;
    return false;
}

static size_t audit_view(const View *v) {
    return v->blob->len;
}

static void close_view(View *v) {
    if (v->owned)
        blob_put(v->blob);

    v->blob = NULL;
}

static size_t process(bool reject, bool retain, bool audit) {
    Request r = { blob_new(12) };
    if (!r.payload)
        return 0;

    View v = open_view(&r, retain);
    bool ok = validate_request(&r, reject);

    size_t result = 0;
    if (!ok && audit)
        result = audit_view(&v);

    close_view(&v);

    if (r.payload)
        blob_put(r.payload);

    return result;
}
```

这次危险操作不是 `memcpy`，而是：

**二、授权检查失配：检查了对象 A，却返回了对象 B**

第二个案例完全不涉及内存生命周期。

假设一个文档系统允许按文档名称访问，也允许指定某个历史版本：

```C
Response read_document(User *user, Request *req) {
    Document *visible = lookup_by_slug(req->slug);
    if (!visible)
        return not_found();

    if (!can_read(user, visible->tenant_id))
        return forbidden();

    Document *actual = visible;

    if (req->revision_id != 0)
        actual = lookup_revision(req->revision_id);

    if (!actual)
        return not_found();

    return send_content(actual->content);
}
```

假设系统的安全要求是：

> 用户只能读取自己有权限访问的租户中的文档内容。
> 
>

> **`lookup_revision()`**** 返回的对象，是否一定属于已经检查过权限的租户？**

> 

**1．两种竞争解释**

**2．整个框架如何处理**

> 当权限检查后重新选择资源，应核查最终操作对象是否仍处于原授权范围。
>

**3．区分性查询是什么？**

```Plain Text
查询：

结果 A：
查询同时校验 parent_document_id 或所属租户。

更新：

```

假设调查发现，它只按全局编号查询，且请求参数没有额外绑定检查，则可以构造以下验证模型：


这说明的问题是：

**授权检查存在，但它约束的对象与最终被访问的对象不一致。**

**1．待检测程序：一个看似有容量检查的数据复制函数**

假设某个程序需要复制若干数据项；开启 `include_meta` 后，还要额外复制两个元数据项。

下面是待分析的核心代码：

```C
#include <stdbool.h>
#include <stdint.h>
#include <stdlib.h>
#include <string.h>

enum { MAX_ITEMS = 32, META_ITEMS = 2 };

typedef uint32_t Item;

typedef struct {
    Item *data;
    size_t capacity;          // 容量单位：Item 的个数
} Buffer;

static bool buffer_init(Buffer *out, size_t cap) {
    if (cap == 0 || cap > MAX_ITEMS)
        return false;

    out->data = malloc(cap * sizeof(Item));
    if (!out->data)
        return false;

    out->capacity = cap;
    return true;
}

static size_t emitted_count(size_t n, bool include_meta) {
    return n + (include_meta ? META_ITEMS : 0);
}

static bool write_items(Buffer *out, const Item *src,
                        size_t src_count,
                        size_t n, bool include_meta) {
    if (n > out->capacity)
        return false;

    size_t m = emitted_count(n, include_meta);

    if (m > src_count)
        return false;

    memcpy(out->data, src, m * sizeof(Item));
    return true;
}

static bool process_frame(size_t requested, bool include_meta) {
    if (requested == 0 || requested > MAX_ITEMS)
        return false;

    Buffer out;
    if (!buffer_init(&out, requested))
        return false;

    Item src[MAX_ITEMS + META_ITEMS] = {0};

    bool ok = write_items(
        &out, src, MAX_ITEMS + META_ITEMS,
        requested, include_meta
    );

    free(out.data);
    return ok;
}
```

分析入口是 `process_frame()`，假设调用方可以选择 `requested` 和 `include_meta`。

这个案例有三个容易混淆的长度：

**真正需要验证的性质是 ****`m <= out->capacity`****。代码直接检查的却是 ****`n <= out->capacity`****。**

但系统不能只凭这句话立即报漏洞：被调函数是否真的扩大长度、调用者是否预留额外空间、相关分支是否可达，都需要证据。

主结果建议报告：

主要消融依次为：

1. 去掉语义对齐，直接基于自然语言分歧规划。

2. 去掉区分性选择，使用相关性或随机查询。

3. 去掉依赖更新，重新把全部历史交给模型判断。

4. 取消调查员的信息隔离。

5. 去掉符号执行。

建议按约 **12—14 周**推进：

第一阶段是重要决策点。如果分歧大多只是措辞不同，或有效查询解决的样本很少，就应调整问题范围；如果静态查询已能解释收益，则不应为了增加模块而扩大符号执行部分。

最终可争取的贡献表述为：

1. **面向竞争性漏洞解释的程序语义对齐与关键前提定位方法。**

2. **考虑程序依赖、后端能力和证据边界的区分性查询生成与选择方法。**

3. **结合按需符号验证、依据证据范围更新推断的协作协议，以及相应机制评测资源。**

这些贡献中，第一、二项需要具体算法和受控实验支撑。符号执行 Agent 的价值应体现为：**在合适的争议上，以可审查的环境取得有效证据，并带来可重复的判断改善。** 只有证明这些收益超过普通探索、直接验证和同预算单 Agent，才适合进一步主张较强创新。



## 13\. Agent 角色对应关系

**当前六个 Agent 都能对应到你列出的人工审计任务，但并不是“一名人工岗位对应一个 Agent”。** 更准确的设计方式是：从人工审计流程中提取不同的认知任务，再按输入、输出和职责边界进行拆分。

例如，一名 AppSec 工程师在现实中可能同时完成漏洞发现、防护审查、争议分析和验证规划；方案将这些任务分给不同 Agent，以便控制协作过程并评价各环节的贡献。

**六个 Agent 与人工角色的对应关系如下。**

这里有几个映射需要特别讲清楚。

**第一，风险分析和防护分析，来自安全审查员工作的两个互补方向。**

现实中的安全审查员通常既检查“漏洞怎样发生”，也检查“已有机制是否阻止它发生”。因此，两个 Agent 可以理解为对同一专业岗位的职责拆分：

- **风险分析**关注危险操作、攻击者影响及违例路径。

- **防护分析**关注防护条件是否覆盖相同对象、状态和路径。

这种拆分便于独立分析和发现隐含假设，但不能强制两者对立。风险分析员可以撤回候选；防护分析员找不到依据时，应明确报告。

**防护依据分析 Agent 不宜直接对应成“代码作者 Agent”。** 你给出的流程中，作者负责提供事实与背景，并不负责坚持代码安全。让模型扮演作者并自动辩护，容易生成源码中不存在的设计保证。

**第二，分歧诊断 Agent 最接近“资深 AppSec 工程师处理争议”的任务。**

它承担的是技术性分析，例如：

> 一个审查员说检查有效，另一个说仍会越界。双方是否讨论同一次访问？检查的是哪个值？危险操作使用的还是这个值吗？
> 
> 

对应到你的人工角色体系：

**它不是人工流程中一个通行的独立岗位名称，而是本研究抽象出的功能角色。**

Moderator 可以为“保持讨论聚焦”提供流程启发，但 Moderator 的流程主持职责不足以承担上述程序语义判断。因此，不建议把“分歧诊断员”等同于“主持人”。

**第三，查询规划与事实调查，对应人工审计中的“制定调查计划”和“执行调查”。**

两者分开后，职责会更清楚：

前者决定**查什么、为什么查**；后两者负责取得不同深度的证据。人工审计中，这些工作可能由同一工程师完成，你的方案通过拆分来研究查询决策及信息隔离是否有益。

事实调查 Agent 对应作者的“事实解释任务”时，也只能依据可访问的源码和资料回答。它不能模拟真实作者未提供的业务意图或设计承诺。

**第四，符号执行 Agent 对应验证专家的工作方式，职责范围应窄于完整渗透测试。**

在当前方案中，它主要复现以下人工工作：

1. 将怀疑的问题变成明确检查目标；

2. 确定入口、输入域和环境假设；

3. 准备验证环境；

4. 调用分析工具；

5. 检查结果是否真正支持原先主张；

6. 记录未覆盖的范围。

它可以交付“指定模型内存在违例见证”，但这不自动等于已经完成真实攻击入口验证、完整 PoC 或漏洞可利用性确认。后者属于更完整的白盒安全评估任务，可以作为扩展。

**另外，Moderator 和 Scribe 的职责应保留在框架中，但可以由程序化模块承担。**

Joern 和 GraphRAG 则作为这些角色使用的基础设施：

- **Joern**支持分析员和调查员定位程序结构、追踪候选依赖。

- **GraphRAG**支持检索历史调查经验和相关记录。

- **证据账本**负责可靠记录与状态管理；GraphRAG 负责从这些记录中检索信息。

不需要额外设计一个“Joern 人工角色”或“GraphRAG 人工角色”。

**用之前的容量例子，人工流程与 Agent 流程可以直接对应起来。**

因此，论文中最合适的设计依据是：**从人工安全审计中提取发现、独立复核、争议归因、验证规划、事实调查和深度验证六类任务，并用明确的证据交接协议组织协作。**

其中，分歧诊断与查询规划是你重点研究的职责拆分；它们的创新性仍应由具体算法和实验收益支撑，人工岗位对应关系主要用于解释设计来源。
