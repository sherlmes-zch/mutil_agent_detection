# 多智能体 PrimeVul 漏洞检测改造计划

## 1. 总体目标

基于 LangChain 和 LangGraph，构建一个由程序语义分歧驱动的多智能体静态漏洞检测系统。

系统针对每个 PrimeVul 函数样本，先让风险路径分析员和保护依据分析员独立分析同一份首轮材料，再由分歧诊断、区分性查询、事实调查和证据更新模块逐步缩小关键程序前提的不确定性。

核心闭环为：

```text
共同首轮输入
  -> 风险解释与保护解释
  -> 语义分歧诊断
  -> 关键前提定位
  -> 区分性查询规划
  -> 按需事实调查或符号验证
  -> 证据依赖更新
  -> 保守漏洞判断与审计报告
```

## 2. 已完成工作

### 2.1 协议层

已在 `src/mutil_agent_detection/protocols/models.py` 中建立共享数据协议，包括：

- `AnalysisInput`：单个样本的分析输入；
- `ProgramScope`、`SourceSnapshot`、`SourceLocation`：程序范围、源码版本和稳定锚点；
- `Claim`：风险、保护和事实主张；
- `Dispute`：共同事实、竞争前提和决定性前提；
- `QuerySpec`、`QueryOutcome`：查询目标、后端、预算和结果分支；
- `Evidence`：工具结果、适用范围、假设和分析边界；
- `AuditState`、`AuditEvent`：单样本 LangGraph 状态和审计轨迹；
- `MemoryRecord`：带来源和适用条件的长期调查经验；
- `FinalReport`：预测、解释、证据和未决问题。

协议层已经明确区分事实、假设、预测、未知状态和工具分析边界，并禁止测试样本之间共享当前审计结论。

### 2.2 LangGraph 最小编排骨架

已在 `src/mutil_agent_detection/workflow.py` 中建立状态图：

```text
initialize
  -> prepare_skeleton
  -> risk_analysis ─┐
                    ├─> merge_analyses
  -> protection_analysis ┘
  -> diagnose
  -> retrieve_memory
  -> plan_queries
  -> select_query
      ├─ 有查询 -> execute_query -> update_evidence
      │                         ├─ 继续调查 -> plan_queries
      │                         └─ 停止 -> finalize
      └─ 无查询 -> no_query_finalize
```

Agent、Joern、GraphRAG 和符号执行通过 `WorkflowHandlers` 注入。当前默认实现只返回保守的 `unknown` 或 `inconclusive`，不会伪造漏洞结论。

### 2.3 PrimeVul 数据适配和批量运行

已实现 JSONL 流式读取、字段规范化、数据质量报告、paired 样本关联和 `AnalysisInput` 转换；批量运行器为每条样本建立独立 LangGraph 审计状态，并隔离单样本错误。

### 2.4 百炼和 Joern 接入

已实现百炼 OpenAI 兼容模型配置、风险/保护结构化 Agent adapter、Joern C/C++ 函数级 CPG 和局部骨架查询。仓库上下文模式由 `--context-mode repository` 选择，RepositoryManager 会复用缓存、从本地源码缓存或远程 HTTPS 获取精确提交，并创建 detached worktree。完整仓库只用于 Joern 分析；首轮 Agent 仍只接收目标函数和共享的局部骨架。

## 3. Agent 输入协议

### 3.1 共同首轮输入

风险路径分析员和保护依据分析员必须独立读取同一个 PrimeVul 函数版本，并使用相同的首轮证据：

- PrimeVul 的 `func` 源码；
- 函数名和函数内相对行号；
- 项目名、文件名、提交版本等元数据；
- 可用时的 Joern 局部代码骨架；
- 当前程序范围和未解析依赖；
- 相同的初始预算。

两者不能在首轮看到对方的输出。区别只来自系统提示、分析任务和输出结构。

### 3.2 风险路径分析员

首轮回答：

- 哪个操作可能违反安全条件；
- 需要哪些路径条件和对象关系才能触发；
- 哪些数据流、状态变化或调用关系构成风险；
- 风险解释依赖哪些尚未确认的程序前提。

输出风险主张、候选触发路径和风险前提。

### 3.3 保护依据分析员

首轮回答：

- 哪些检查、不变量、初始化或调用契约可能阻断风险；
- 保护措施约束的是哪个对象和哪条路径；
- 保护条件在哪些状态下成立；
- 是否存在保护失效、绕过或范围不一致。

输出保护主张、保护路径和保护前提。

### 3.4 上下文边界

不默认把整个仓库直接交给两个首轮 Agent。输入采用分层范围：

```text
PrimeVul 函数
  -> Joern 局部骨架
  -> 按需展开的文件、类型、宏和调用关系
  -> 必要时的仓库快照和符号执行入口
```

文件和仓库是后续事实调查员的取证范围，不是首轮 Agent 的无限上下文。

## 4. 第三阶段：PrimeVul 数据适配

这是下一步首先执行的工作。

### 4.1 原始记录读取

实现 JSONL 流式读取和原始记录校验，保留以下字段：

- `idx`、`project`、`commit_id`；
- `project_url`、`commit_url`、`commit_message`；
- `func`、`target`、`func_hash`；
- `file_name`、`file_hash`；
- `cwe`、`cve`、`cve_desc`、`nvd_url`。

空值、字符串 `"None"`、缺失字段和类型异常都要显式记录，不能静默丢弃。

### 4.2 样本规范化

建立稳定样本标识，至少结合：

```text
dataset + idx + project + commit_id + file_name + func_hash
```

保留原始函数文本，同时生成供模型使用的规范化视图。超长函数不能直接截断；需要记录摘要、局部窗口和省略范围。

### 4.3 数据质量报告

统计并保存：

- 标签和项目分布；
- CWE 分布；
- 函数长度分布；
- 缺失文件名和文件哈希；
- 重复 `idx` 和重复函数；
- 无法定位仓库源码的样本；
- paired 数据的配对完整性。

## 5. 第四阶段：映射到 `AnalysisInput`

数据集样本映射关系为：

```text
func           -> source
函数名          -> function_name
project/commit -> SourceSnapshot
文件和位置      -> ProgramScope
target         -> expected_label
PrimeVul 元数据 -> metadata
```

需要区分两种运行模式：

### 5.1 函数-only 模式

只使用目标函数和有限元数据，明确标记：

- 跨过程关系未解析；
- 外部类型和宏可能缺失；
- Joern 分析范围受限；
- 缺少上下文不能解释为不存在保护。

### 5.2 仓库上下文模式

根据 `project_url`、`commit_id`、`file_name` 和 `file_hash` 获取对应源码快照，并记录：

- 源码版本；
- 文件定位结果；
- 工具配置；
- 依赖版本；
- 上下文获取失败或部分成功原因。

## 6. 第五阶段：实现两个首轮 Agent

使用 LangChain 的结构化输出，让两个 Agent 分别生成 `Claim`。

### 风险路径分析员

输出危险操作、候选路径、对象关系、触发条件和风险前提。

### 保护依据分析员

输出检查、不变量、调用约束、保护路径和保护前提。

两个 Agent 的初始事实输入保持一致；角色差异只体现在任务说明和分析方向。默认不把对方结论放入提示词。

## 7. 第六阶段：Joern 局部程序骨架

在两个 Agent 首轮分析前生成同一份局部骨架，包含：

- 入口函数；
- 危险操作候选；
- 调用关系；
- 参数和返回值；
- 关键分支；
- 变量定义和使用；
- 初步数据流；
- 指针/类型强转、解引用、数组或指针索引；
- 指针算术、整数算术及比较/边界条件；
- 函数形参与已知输入 API 等数据来源候选；
- 相关检查；
- 目标对象；
- 源码行号；
- 未解析调用和依赖。

上述结构化线索均须尽可能关联准确文件、行号、代码片段及可用类型信息。Joern 骨架只作为 Agent 检查源码的导航和证据线索，不能替代真实源码，也不能直接证明存在漏洞、所有权、容量单位或外部函数契约。

## 8. 第七阶段：语义分歧诊断

分歧诊断 Agent 接收两个独立主张和同一份程序骨架，输出：

- 共同讨论的操作和对象；
- 共同确认的事实；
- 对象、变量版本和路径是否一致；
- 真正冲突的前提；
- 只是缺少证据的前提；
- 决定最终结论的关键前提；
- 每个前提的源码锚点。

必须避免把不同调用路径、不同对象或不同状态误判为逻辑冲突。

## 9. 第八阶段：查询规划与事实调查

### 9.1 查询规划

查询设计员根据 `Dispute`、程序骨架、记忆经验和剩余预算生成 `QuerySpec`。每个查询要提前声明：

- 目标前提；
- 程序范围；
- 查询类型和后端；
- 可能结果；
- 每个结果允许的状态更新；
- 证据要求；
- 成本和环境假设。

### 9.2 事实调查

事实调查员按查询范围获取：

- 源码位置；
- 调用者和被调函数；
- 宏和类型定义；
- 分配关系；
- 参数映射；
- 字段写入和副作用；
- 路径条件。

任何“未发现”都必须带分析覆盖范围，不能直接解释为“不存在”。

## 10. 第九阶段：证据更新与符号执行

证据更新路径为：

```text
工具事实
  -> 支持或否定程序前提
  -> 更新依赖该前提的主张
  -> 更新漏洞预测
```

符号执行只在静态分析无法解决、且关键前提对最终判断有明显影响时按需调用。返回结果必须区分：

- 找到模型内反例；
- 真实入口可达；
- 原项目重放成功；
- 不可达；
- 超时；
- 环境不完整。

## 11. 第十阶段：评测和实验

建议先使用 `primevul_test_paired.jsonl` 做平衡、可解释实验，再运行完整的 `primevul_test.jsonl`。

至少比较：

- 单 Agent 基线；
- 双 Agent、无分歧诊断；
- 加入分歧诊断；
- 加入区分性查询；
- 加入证据更新；
- 加入 GraphRAG；
- 加入按需符号执行。

报告：

- Precision、Recall、F1、FPR、PR-AUC；
- `unknown` 比例；
- 关键前提解决率；
- 有效查询率和重复查询率；
- token、工具调用次数和时间；
- 初始错误纠正率；
- 正确判断被改错率；
- 漏洞版/修复版判断一致性。

## 12. 数据隔离和缓存规则

- 漏洞版和修复版分别建立 `AuditState`；
- 不把一侧的结论、补丁说明或标签传给另一侧；
- 长期经验库只由训练集和允许的外部资料构建，并在测试前冻结；
- 测试样本只写入当前审计轨迹；
- 缓存键必须包含源码版本、文件、函数哈希、上下文模式、工具配置和依赖条件；
- 不能只按函数名或项目名复用程序分析结果。

## 13. 推荐里程碑

### M1：数据和协议闭环

完成 JSONL 读取、质量报告、样本规范化和 `AnalysisInput` 转换。

### M2：函数-only Agent 闭环

实现风险路径分析员、保护依据分析员和结构化输出，使用少量 paired 样本验证状态流转。

### M3：Joern 增强

生成双方共享的局部程序骨架，并接入基础事实查询。

### M4：研究核心闭环

实现分歧诊断、`QuerySpec`、查询选择和证据依赖更新。

### M5：仓库上下文和符号验证

接入源码快照、跨过程查询、SMT 和按需符号执行。

### M6：完整实验

完成 paired 对照、全量测试、消融实验、成本统计和审计轨迹分析。

4. 实现查询规划、事实调查和证据依赖更新；
5. 再逐步加入 GraphRAG 与按需符号执行。
